## 3.2. User Stories

Este capítulo presenta la especificación de requisitos de QualiTrack a partir del análisis del problema, los segmentos objetivo y el alcance construido durante el desarrollo del producto. La especificación cubre los productos de la solución: la landing page pública, la aplicación web frontend, la aplicación móvil y los servicios backend RESTful implementados con una arquitectura basada en bounded contexts. Las User Stories (US) se agrupan en Epics; las Technical Stories (TS), que describen capacidades técnicas del backend sin interacción directa de un usuario final, se presentan al final de la sección.

### Technical Stories

Las Technical Stories describen capacidades técnicas del backend que no representan una interacción directa con un usuario final. Por ello no pertenecen a una Epic.

| **Story ID** | **User** | **Priority** | **Epic** |
|---|---|---|---|
| TS01 | Developer | Alta | No aplica |

| **Title** | Autenticar usuarios mediante la API |
|---|---|
| **Description** | Como Developer deseo autenticar usuarios mediante la API para obtener una sesión válida para las aplicaciones de QualiTrack. |
| **Acceptance Criteria** | **Escenario 1: Solicitud válida**<br>**Dado que** se recibe una solicitud `POST` en `/api/v1/authentication/sign-in` con el usuario y la contraseña de una cuenta activa,<br>**Cuando** el servicio la procesa,<br>**Entonces** responde `200 OK` con el token de acceso y los roles del usuario.<br><br>**Escenario 2: Credenciales inválidas**<br>**Dado que** el usuario no existe, la contraseña es incorrecta o la cuenta está inactiva,<br>**Cuando** el servicio procesa la solicitud,<br>**Entonces** responde `401 Unauthorized` sin indicar cuál de los datos falló. |

| **Title** | Liberar un lote mediante la API |
|---|---|
| **Description** | Como Developer deseo liberar un lote existente mediante la API para soportar la revisión realizada por un responsable autorizado. |
| **Acceptance Criteria** | **Escenario 1: Solicitud válida**<br>**Dado que** se recibe una solicitud `POST` en `/api/v1/laboratories/{laboratoryId}/environments/{environmentId}/products/{productId}/batches/{batchId}/releases` con la fecha y las notas de la liberación,<br>**Cuando** el servicio la procesa,<br>**Entonces** responde `201 Created` con el lote liberado y su firma digital (usuario, fecha y huella SHA-256).<br><br>**Escenario 2: Datos inválidos**<br>**Dado que** faltan datos obligatorios o no tienen un formato válido,<br>**Cuando** el servicio procesa la solicitud,<br>**Entonces** responde `400 Bad Request` sin aplicar cambios.<br><br>**Escenario 3: Sin rol de calidad**<br>**Dado que** el usuario no es responsable de calidad y supervisión,<br>**Cuando** el servicio procesa la solicitud,<br>**Entonces** responde `403 Forbidden` sin aplicar cambios.<br><br>**Escenario 4: Lote cerrado**<br>**Dado que** el lote ya fue liberado o rechazado,<br>**Cuando** el servicio procesa la solicitud,<br>**Entonces** responde `409 Conflict` sin aplicar cambios. |
