# Capítulo VII: DevOps Practices

### 7.1. Continuous Integration

<p>
En esta sección se describe cómo el equipo IoTech aplica la práctica de Integración Continua en QualiTrack. Cada Pull
Request hacia <code>develop</code> o <code>main</code> dispara de forma automática un pipeline en
<strong>GitHub Actions</strong> que instala las dependencias del producto, ejecuta su suite de pruebas y, en el caso de
la aplicación web, genera el build de producción. De esta manera, antes de aprobar el merge de un Pull Request, el
equipo verifica en el mismo Pull Request que los cambios compilan y que no rompen ninguna prueba existente.
</p>

<p>
Se implementó un pipeline de integración continua para cada uno de los productos de software:
</p>

| Producto | Repositorio | Workflow | Disparador | Qué valida |
|---|---|---|---|---|
| Backend Web Services | [Qualitrack-Platform](https://github.com/Experimentos-1ASI0732-2620-9104/Qualitrack-Platform) | `.github/workflows/ci.yml` | Pull Request hacia `develop` o `main` | Compilación y pruebas unitarias y de integración del API con Maven (229 pruebas). |
| Frontend Web Application | [Qualitrack-WebApplication](https://github.com/Experimentos-1ASI0732-2620-9104/Qualitrack-WebApplication) | `.github/workflows/ci-build.yml` | Pull Request hacia `develop` o `main` | Pruebas unitarias de Vitest (870 pruebas) y build de producción de Angular. |
| Mobile Application | [Qualitrack-MobileApplication](https://github.com/Experimentos-1ASI0732-2620-9104/Qualitrack-MobileApplication) | `.github/workflows/ci.yml` | Pull Request desde una rama `feature/*` hacia `develop` | Análisis estático con `flutter analyze` y pruebas de Flutter (174 pruebas). |

#### 7.1.1. Tools and Practices

<p>
Las herramientas utilizadas para implementar la integración continua son las siguientes:
</p>

| Herramienta | Uso en la integración continua |
|---|---|
| GitHub | Repositorios del proyecto y Pull Requests, organizados con el flujo GitFlow descrito en la sección 5.1.2. |
| GitHub Actions | Servidor de integración continua; ejecuta los workflows en máquinas virtuales `ubuntu-latest` en cada Pull Request. |
| Eclipse Temurin JDK 26 + caché de Maven | Entorno de Java usado para compilar y probar el backend (`actions/setup-java`). |
| Apache Maven | Gestión de dependencias, compilación y ejecución de pruebas (`mvn -B test`). |
| JUnit 5, Spring Boot Test y MockMvc | Suites de pruebas unitarias y de integración del backend (secciones 6.1.1 y 6.1.2). |
| Node.js 22 + caché de npm | Instalación reproducible de dependencias con `npm ci` (`actions/setup-node`). |
| Angular CLI + Vitest | Pruebas unitarias (`npm test -- --watch=false`) y build de producción (`npm run build`) de la aplicación web. |
| Flutter 3.44.3 (`subosito/flutter-action`) | Instalación de una versión fija de Flutter con caché, análisis estático y pruebas de la aplicación móvil. |

<p>
Las prácticas de integración continua que adopta el equipo son:
</p>

<ul>
  <li>
    <strong>Integración frecuente en un repositorio común:</strong> cada integrante trabaja en una rama
    <code>feature/*</code> creada desde <code>develop</code> y la integra mediante un Pull Request, siguiendo GitFlow y
    Conventional Commits.
  </li>
  <li>
    <strong>Build automatizado:</strong> la compilación no depende de la máquina de un integrante; el pipeline parte
    siempre de un entorno limpio e instala versiones fijas de las herramientas (JDK 26, Node.js 22 y Flutter 3.44.3).
    La versión de Flutter se fijó para que una nueva versión estable no haga fallar todos los Pull Requests.
  </li>
  <li>
    <strong>Build auto-verificable (self-testing build):</strong> el mismo pipeline ejecuta la suite de pruebas del
    producto; si alguna prueba falla, el pipeline termina en error. En la aplicación web las pruebas se ejecutan antes
    del build, y en la aplicación móvil el análisis estático se ejecuta antes de las pruebas.
  </li>
  <li>
    <strong>Retroalimentación rápida y visible:</strong> el resultado aparece en el Pull Request y en la pestaña
    <em>Actions</em> del repositorio. El pipeline del backend termina en alrededor de un minuto.
  </li>
  <li>
    <strong>Mínimos permisos:</strong> los workflows de integración declaran <code>permissions: contents: read</code>,
    por lo que solo pueden leer el código del repositorio.
  </li>
  <li>
    <strong>Corregir primero un build roto:</strong> un Pull Request con el pipeline en rojo no se integra hasta que el
    pipeline vuelva a estar en verde.
  </li>
</ul>

#### 7.1.2. Build & Test Suite Pipeline Components

<p>
El siguiente diagrama resume el flujo de integración continua de QualiTrack:
</p>

```mermaid
flowchart LR
    pr["Pull Request a develop o main"] --> gha["GitHub Actions"]
    gha --> be["Backend: CI"]
    gha --> web["Web: CI build (PR)"]
    gha --> mob["Mobile: CI"]
    be --> b1["Checkout"] --> b2["JDK 26 + caché Maven"] --> b3["mvn -B test"]
    web --> w1["Checkout"] --> w2["Node.js 22 + caché npm"] --> w3["npm ci"] --> w4["Pruebas unitarias (Vitest)"] --> w5["Build de producción"]
    mob --> m1["Checkout"] --> m2["Flutter 3.44.3"] --> m3["flutter pub get"] --> m4["flutter analyze"] --> m5["flutter test"]
```

<p>
<strong>Pipeline del Backend Web Services</strong> (<code>Qualitrack-Platform/.github/workflows/ci.yml</code>, job
<em>test</em>):
</p>

| # | Componente (step) | Descripción |
|---|---|---|
| 1 | Trigger | Se ejecuta con cada Pull Request hacia `develop` o `main`. |
| 2 | Checkout | Descarga el código del commit que se va a validar (`actions/checkout@v4`). |
| 3 | Set up JDK 26 | Instala Eclipse Temurin JDK 26 y reutiliza la caché de dependencias de Maven (`actions/setup-java@v4`). |
| 4 | Test | Ejecuta `mvn -B test`: compila el proyecto y corre las pruebas unitarias y de integración. |

<p>
<strong>Pipeline de la Frontend Web Application</strong>
(<code>Qualitrack-WebApplication/.github/workflows/ci-build.yml</code>, job <em>build</em>):
</p>

| # | Componente (step) | Descripción |
|---|---|---|
| 1 | Trigger | Se ejecuta con cada Pull Request hacia `main` o `develop`. |
| 2 | Checkout | Descarga el código del commit (`actions/checkout@v5`). |
| 3 | Set up Node.js 22 | Instala Node.js 22 con caché de npm (`actions/setup-node@v5`). |
| 4 | Instalar dependencias | Instala exactamente las versiones del `package-lock.json` con `npm ci`. |
| 5 | Pruebas unitarias | Ejecuta `npm test -- --watch=false` (Vitest con Angular TestBed). |
| 6 | Build de producción | Compila la aplicación con `npm run build`; si hay errores de compilación, el pipeline se detiene. |

<p>
<strong>Pipeline de la Mobile Application</strong>
(<code>Qualitrack-MobileApplication/.github/workflows/ci.yml</code>, job <em>verify</em>):
</p>

| # | Componente (step) | Descripción |
|---|---|---|
| 1 | Trigger | Se ejecuta con cada Pull Request hacia `develop` cuya rama de origen empieza con `feature/`. |
| 2 | Checkout | Descarga el código del commit (`actions/checkout@v4`). |
| 3 | Set up Flutter | Instala Flutter 3.44.3 del canal estable con caché (`subosito/flutter-action@v2`). |
| 4 | Dependencias | Ejecuta `flutter pub get`. |
| 5 | Análisis estático | Ejecuta `flutter analyze` con las reglas de `analysis_options.yaml` (sección 6.2). |
| 6 | Pruebas | Ejecuta `flutter test`. |

<p>
<strong>Evidencia de ejecución:</strong>
</p>

| Pipeline | Resultado |
|---|---|
| Backend - CI | Exitoso en el Pull Request de la versión 1.2.0: 229 pruebas, 0 fallos, `BUILD SUCCESS` en aproximadamente 1 minuto. |
| Web - CI build (PR) | Exitoso en el Pull Request de la versión 2.5.0: 128 archivos y 870 pruebas de Vitest aprobados y build de producción generado. |
| Mobile - CI | Exitoso en el Pull Request de la rama `feature/refactor-ui`: `flutter analyze` sin observaciones y 174 pruebas aprobadas. |
