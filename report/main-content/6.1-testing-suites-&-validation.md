# Capítulo VI: Product Verification & Validation

### 6.1. Testing Suites & Validation

<p>
En esta sección se presentan las suites de pruebas automatizadas elaboradas por el equipo IoTech para verificar el
correcto funcionamiento de QualiTrack. Cada producto de código cuenta con su propia suite, que se ejecuta en GitHub
Actions en cada Pull Request hacia <code>develop</code> y <code>main</code> (sección 7.1), de modo que ningún cambio se
integra si alguna prueba falla. Al 13/11/2026 las tres suites se encuentran aprobadas:
</p>

| Producto | Repositorio | Herramientas | Archivos de prueba | Pruebas ejecutadas en CI |
|---|---|---|---|---:|
| Backend Web Services (RESTful API) | [Qualitrack-Platform](https://github.com/Experimentos-1ASI0732-2620-9104/Qualitrack-Platform/tree/develop/src/test/java/com/iotech/qualitrack/platform) | JUnit 5, Spring Boot Test, MockMvc | 44 clases | 229 |
| Frontend Web Application | [Qualitrack-WebApplication](https://github.com/Experimentos-1ASI0732-2620-9104/Qualitrack-WebApplication/tree/develop/src/app) | Vitest con Angular TestBed | 128 archivos `.spec.ts` | 870 |
| Mobile Application | [Qualitrack-MobileApplication](https://github.com/Experimentos-1ASI0732-2620-9104/Qualitrack-MobileApplication/tree/develop/test) | flutter_test, bloc_test | 18 archivos | 174 |

<p>
Las herramientas de prueba utilizadas son las siguientes:
</p>

| Herramienta | Producto | Uso dentro de la suite |
|---|---|---|
| JUnit 5 (Jupiter) | Backend | Framework base para definir y ejecutar los casos de prueba, incluidas las pruebas parametrizadas. |
| Spring Boot Test + MockMvc | Backend | Levanta el contexto de Spring y ejercita los endpoints REST sobre una base de datos de prueba, comprobando códigos HTTP, recursos devueltos y permisos por rol. |
| Maven Surefire | Backend | Ejecución automatizada de las pruebas con <code>mvn -B test</code>. |
| Vitest + Angular TestBed | Web | Pruebas de assemblers, servicios, stores, validadores y componentes de cada Bounded Context (<code>ng test</code>). |
| Playwright (Chromium) | Web | Scripts de navegador en <code>tests/*.mjs</code> que recorren las vistas principales (sección 6.1.4). |
| flutter_test + bloc_test | Mobile | Pruebas del dominio, casos de uso, infraestructura HTTP, BLoC, pantallas y reglas de dependencia entre capas (<code>flutter test</code>). |

#### 6.1.1. Core Entities Unit Tests

<p>
Las pruebas unitarias validan, de forma aislada y sin levantar Spring ni la base de datos, las reglas del dominio de
cada Bounded Context: aggregates, entities, value objects y commands. Cada prueba sigue el patrón
<em>Arrange - Act - Assert</em>: se construye la entidad o el command, se ejecuta el comportamiento del dominio y se
verifica el estado resultante o la excepción esperada.
</p>

#### 6.1.2. Core Integration Tests

<p>

<em>application</em> (command y query services), <em>domain</em> e <em>infrastructure</em> (repositorios JPA), junto con

</p>

#### 6.1.3. Core Behavior-Driven Development

<p>
En este sprint no se elaboraron pruebas de aceptación BDD con archivos <code>.feature</code>; los escenarios de
aceptación de cada Technical Story se verifican con las pruebas de integración de su endpoint (sección 6.1.2). Por
ejemplo, el criterio de aceptación de la gestión de alertas (reconocer y resolver una alerta de desviación como el
usuario autenticado) se valida en <code>RestApiIntegrationTests</code> y <code>ComplianceAlertsIntegrationTests</code>, y
el de onboarding (pagar la suscripción antes de crear el laboratorio) en <code>OnboardingIntegrationTests</code>.
</p>

#### 6.1.4. Core System Tests

<p>
Las pruebas de sistema validan la Frontend Web Application como la usa el responsable de calidad: un navegador real
(Chromium, automatizado con <strong>Playwright</strong>) opera las vistas principales y verifica la navegación, los
formularios, las validaciones, los mensajes de error y el diseño responsive. Los scripts responden las llamadas al API
con fixtures, por lo que ninguna prueba llega a la plataforma real; se ejecutan con Node contra la aplicación en
ejecución (<code>ng serve</code>), por ejemplo <code>node tests/responsive.mjs</code>, y la variable
<code>WEB_URL</code> permite cambiar la dirección de la aplicación.
</p>

<p>
<strong>Ubicación:</strong> <code>tests/</code> (repositorio Qualitrack-WebApplication).
</p>

| Script | Vista validada |
|---|---|
| `alerts-browser.mjs` | Bandeja de alertas activas, grupos por severidad, panel de detalle, reconocimiento y resolución de alertas. |
| `dashboard-browser.mjs` | Dashboard: selección de telemetría, unidades, suscripción, idioma español y errores parciales del API. |
| `inventory-browser.mjs` | Inventario: catálogo, registro de materiales, validaciones, códigos rechazados y revisión de recepciones. |
| `onboarding-browser.mjs` | Onboarding del laboratorio después de la suscripción. |
| `report-generator-browser.mjs` | Generador de reportes: descargas, periodo inválido y reporte rechazado. |
| `responsive.mjs` | Diseño de las vistas principales en distintos anchos de pantalla. |
| `stripe-catalog-browser.mjs` | Catálogo de planes de Stripe; requiere un backend local aislado (<code>LOCAL_API=1</code>) porque crea cuentas reales. |

<p>
<strong>Alcance:</strong> estos scripts se ejecutan de forma local y no forman parte del pipeline de integración
continua, que ejecuta las pruebas unitarias de Vitest (sección 7.1). La aplicación móvil consume el mismo RESTful API,
cuyos flujos quedan cubiertos por las pruebas de integración del backend (6.1.2) y por las pruebas de pantallas y BLoC
de la propia aplicación (6.1.1).
</p>

<p>
<strong>Ejecución:</strong> se ejecutaron localmente <code>alerts-browser.mjs</code> y <code>responsive.mjs</code> en
Chromium contra la aplicación en <code>ng serve</code>. El primero verificó la bandeja de alertas activas, el panel de
detalle y la resolución de una alerta en anchos de 320 a 1440 px. El segundo revisó 33 vistas en 9 anchos de pantalla
(297 combinaciones) sin desbordes ni fallos.
</p>

```
$ node tests/alerts-browser.mjs
Alerts browser checks passed

$ node tests/responsive.mjs
Checked 33 views at 320px
...
Checked 33 views at 1440px
{
  "checked": 297,
  "failures": []
}
```
